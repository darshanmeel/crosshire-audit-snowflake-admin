# Query Performance & Workload

What the queries themselves are doing: spilling, queuing, failures, workload shape, repeated query fingerprints, Snowflake's own Query Insights verdicts, pruning effectiveness at partition *and* row level, and a single-query operator probe.

📖 **Full interactive docs → [every query, explained](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance)** — why it matters, what it does, how to read every output column, the ladder rung it stands on, and the caveats.

**The ladder in this domain.** One query stands on `information_schema` as the live twin of the ACCOUNT_USAGE answers (`perf_query_history_live_is`), one is a plan-level probe that no view can replace (`perf_operator_stats_probe`), one stands on `show` because no view carries the account parameter set (`perf_runaway_query_guardrail`), and the remaining eleven climb to `account_usage` — spill, pruning and per-shape rollups simply do not exist on a lower rung. Every file says which rung it is on and why it climbed.

| # | Query | Tier · Rung | What it does |
|--:|---|---|---|
| 01 | [`perf_access_history_summary`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_access_history_summary) | standard · AU | One row per object: how many statements read it, how many wrote it, how many distinct readers and columns — and flags the objects written repeatedly and never read. Reads resolve through `BASE_OBJECTS_ACCESSED`, so a view credits the table underneath it. Enterprise Edition or higher. |
| 02 | [`perf_bytes_scanned_divergence`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_bytes_scanned_divergence) | deep · AU | Reconciles the partitions a *statement* claims to have scanned against the partitions its *tables* report, per query shape, warehouse and day — the check that says whether a scan number can be trusted for sizing or chargeback. Carries the three innocent explanations (cache, query acceleration, non-table sources) as columns. |
| 03 | [`perf_clustering_recommendations`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_clustering_recommendations) | standard · AU | Joins per-table pruning to current table size and picks out the tables that are badly pruned **and** large **and** hot — the only combination where a clustering key repays its serverless cost. Names a candidate, never a key. |
| 04 | [`perf_failed_queries`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_failed_queries) | lite · AU | Failures rolled up by error code, warehouse and statement type: how often, over how many users, and how much execution time each signature burns *before* it dies. |
| 05 | [`perf_operator_stats_probe`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_operator_stats_probe) | deep · IS | Points `GET_QUERY_OPERATOR_STATS()` at **one** query id you already found and returns the plan: which operator took the time, which one spilled, and which scan read nearly every partition. Live, no admin grant, ~14-day reach. |
| 06 | [`perf_query_history_live_is`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_query_history_live_is) | lite · IS | The last few hours of finished statements, live and with no `IMPORTED PRIVILEGES` — the rung to stand on when ACCOUNT_USAGE has not caught up. Carries queuing and failures; carries **no** spill or pruning columns, and says so. |
| 07 | [`perf_query_insights`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_query_insights) | deep · AU | Snowflake's own verdicts, grouped by insight topic and type: how often each fires, across how many distinct query shapes, and a sampled suggestion — the vendor opinion, kept separate from ours. |
| 08 | [`perf_queuing_overload`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_queuing_overload) | standard · AU | Per warehouse per clock hour, the share of statement time lost to queue *overload* — kept strictly apart from provisioning and repair queuing, which are Snowflake's doing, not your concurrency. |
| 09 | [`perf_repeated_query_shapes`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_repeated_query_shapes) | deep · AU | The per-shape rollup `AGGREGATE_QUERY_HISTORY` has already computed: calls, approximate aggregate elapsed hours, median and P99 per call, and the P99-over-median ratio that separates slow SQL from an unstable environment. |
| 10 | [`perf_row_pruning_gap`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_row_pruning_gap) | deep · AU | Row-level pruning beside partition-level pruning for the same table — the gap where a table opens the right micro-partitions and then reads nearly everything inside them, which a partition ratio alone hides. |
| 11 | [`perf_runaway_query_guardrail`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_runaway_query_guardrail) | lite · SHOW | Whether `STATEMENT_TIMEOUT_IN_SECONDS` and `STATEMENT_QUEUED_TIMEOUT_IN_SECONDS` are actually **set** at account level, or whether the number in force is only a Snowflake default nobody chose. A value of `0` means no limit at all. |
| 12 | [`perf_spilling_queries`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_spilling_queries) ★ | standard · AU | Every statement that spilled, ranked by remote spill — the signal that the working set outgrew the warehouse. Remote spill is a defect; local spill alone is a warning. |
| 13 | [`perf_table_pruning_gap`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_table_pruning_gap) | standard · AU | Per-table partition-pruning percentage against the execution hours spent on that table — full scans dressed up as filtered queries, ranked by how much they actually cost in time. |
| 14 | [`perf_workload_hours`](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance#q-perf_workload_hours) | lite · AU | The reference profile: statements, elapsed hours, queuing and scan volume by hour of day, warehouse and statement class — so a change lands in a window that is actually free. An inventory, not a finding. |

<sub>★ = first-audit pick. `AU` = `SNOWFLAKE.ACCOUNT_USAGE` (needs `IMPORTED PRIVILEGES`, lagged 45 min – 6 h depending on the view). `IS` = `INFORMATION_SCHEMA` or a bare built-in table function (live, low-privilege, short reach). `SHOW` = a `SHOW` command read back through `RESULT_SCAN(LAST_QUERY_ID())` (live, snapshot only).</sub>

<sub>**Nothing here has been run against a live Snowflake account.** Thirteen of the fourteen claim `confidence: confirmed-docs` — every view, table function and column named was verified against `docs.snowflake.com`. `perf_runaway_query_guardrail` claims `confidence: unverified` on purpose: it depends on `SHOW` output column labels, which are documented but are not a versioned contract.</sub>

<sub>This is a one-line index — the full write-up (output columns, healthy vs investigate bands, the free→config→spend action ladder, caveats) lives in the [interactive docs](https://learn.crosshire.ch/learn/tech/snowflake/audit/performance). The `.sql` files in this folder are the source of truth.</sub>
